# HexWiki compiler guide

This is the complete writing contract for a source-bounded Open Knowledge
Format (OKF) wiki. It governs model-written notes and the navigation that joins
them. Deterministic source guides and PDF-page gateways are generated by the
engine and are never model-editable.

## Purpose and epistemic status

A HexWiki helps a reader navigate what a declared PDF scope says, how its
argument works, what evidence it offers, and where that evidence stops. It is
not an encyclopedia, fact-check, biography collection, or verdict on the
source's claims.

Every semantic note is an unverified draft. Inclusion means only that the
material occurs in the locked scope. Never turn repetition into corroboration,
reported speech into fact, an author's interpretation into consensus, or an
absence in the selected pages into an absence everywhere.

Generation may use only:

- the current run's immutable staged source under `_ingest/`;
- exact current-run PDF-page gateways under `sources/pdf-pages/`;
- the current run's machine-validated survey under `_plan/`; and
- notes already written in the same fresh candidate.

Never consult a prior wiki, gold/reference wiki, comparison, persistent memory,
shared skill, website, or outside factual knowledge while writing.

## Note vocabulary and locations

Each subject has one canonical home. Do not create aliases or redirects.

| Location | Type | Function |
|---|---|---|
| `overview.md` | Overview | Orient the reader to the scope and its central question. |
| `reading-guide.md` | Reading Guide | Give concrete reading, lookup, and audit paths. |
| `chapters/` | Chapter | Reconstruct the scoped division's architecture. |
| `sections/` | Section | Follow each source division in source order. |
| `cases/` | Case Dossier | Record one narrated incident, record, observation, experiment, or worked example. |
| `concepts/` | Concept | Explain a substantive, methodological, or epistemic idea. |
| `people/` | Person | Describe the author in scope or collect other names by role. |
| `synthesis/` | Synthesis | Analyze argument, claims, recurring features, and controls. |
| `synthesis/open-questions.md` | Open Question | State material questions the scope cannot settle. |
| `sources/` and `reference/` | Source Guide | Deterministic provenance and scope infrastructure. |

Folder `index.md` files and the root `index.md` are catalogs and carry no front
matter. `log.md` is append-only. `_schema/`, `reports/`, and `audit/` are engine
infrastructure.

## Completeness

The accepted survey inventory is the build contract:

- one Chapter note for its scoped hub;
- one Section note for every surveyed section, in source order;
- one Case Dossier for every surveyed episode, including brief mentions;
- one Concept note for every surveyed concept;
- one scope-specific author note and one roster note per other role group;
- five synthesis artifacts: argument map, claim-evidence matrix, motif matrix,
  critical reading, and open questions;
- Overview and Reading Guide notes; and
- complete root and folder catalogs.

A short source deserves short notes, not padding. A passing mention still gets a
brief dossier when it is genuinely a narrated episode. A bibliography entry,
date, name, or word origin is not promoted into an incident merely to satisfy a
count. Architecture floors belong to the profile; a null floor is permission to
follow the source's shape, never permission to omit the list.

## Front matter: OKF v0.2

Every semantic note starts with a valid YAML block like this:

```yaml
---
type: Concept
title: "Exact H1 title"
description: "A retrieval-oriented description containing at least eight useful words."
tags: [scope-id, concept]
semantic_note: true
status: draft
pdf_pages: [12, 13]
sources:
  - { resource: "sources/pdf-pages/page-0012.md", locator: "PDF page 12" }
  - { resource: "sources/pdf-pages/page-0013.md", locator: "PDF page 13" }
generated: { by: "hexwiki", mode: "model-compiled" }
---
```

Rules:

- `type` exactly matches the location table.
- `title` exactly equals the first H1 after front matter.
- `description` is specific enough for retrieval and has at least eight words.
- `tags` is a non-empty list.
- `semantic_note: true` and `status: draft` are constants.
- Never write a `verified` key. OKF v0.2 represents the unverified tier by the
  key's absence; `verified: false` and `verified: []` are both wrong for new
  output.
- `pdf_pages` lists only page numbers actually used by the note, uniquely and in
  ascending order.
- `sources` is a non-empty list of mappings. Every mapping has a `resource`
  pointing to a canonical gateway.
- Every page in `pdf_pages` is linked in the body beside the claim it supports.
- Quote strings when punctuation could be parsed as YAML syntax.

## Shared body rules

After front matter, every semantic note has:

1. an H1 exactly matching `title`;
2. a bold one-sentence orientation;
3. sections appropriate to its type;
4. `## Connections` with links to real related notes; and
5. `## Sources` with direct relative links to the exact PDF-page gateways.

Use ordinary relative Markdown links. From `cases/example.md`, PDF page 12 is
`../sources/pdf-pages/page-0012.md`; from a root note it is
`sources/pdf-pages/page-0012.md`. Every link must resolve. Put a source link next
to the proposition it supports as well as in the final source list when that
makes the locator clearer.

Write only what the cited pages support. Preserve names, dates, locations,
quantities, sequence, and uncertainty exactly as given. Fix obvious extraction
hyphenation in prose without altering the immutable gateway. Quote sparingly;
paraphrase faithfully and keep quotation marks only around words actually on the
page.

## Case Dossier

A Case Dossier uses this order:

1. `## Reported account` — attributed narration with every specific the scope
   supplies.
2. `## Source chain` — who reports what through which intermediary, and any
   apparatus entry that applies.
3. `## Use in the argument` — what the source offers the episode as evidence
   for.
4. `## Evidence limits` — both the support present and the support absent.
5. `## Connections`.
6. `## Sources`.

The Evidence limits section is mandatory and names concrete absences: no second
witness, no named investigator, no primary record, no measurement, no date, an
anonymous intermediary, a translation, or only an authorial summary—whichever
the scoped pages actually warrant. Do not invent an absent control that the
pages provide.

## Concept

Every Concept note defines the idea, explains how the source uses it, and has a
`## Instances in scope` section linking every Case Dossier that genuinely
exhibits it.

Then apply its kind-specific guardrail:

- A substantive concept has `## Evidence status`, distinguishing alleged
  instances from any in-scope document, measurement, or named investigation.
- A methodological or epistemic concept has `## What this licenses and what it
  does not`, with explicit `Supports:`, `Does not support:`, and `Controls absent
  in scope:` statements.

The weak/strong distinction must be concrete. Similar accounts may support a
claim of recurring description; they do not by themselves prove one persistent
cause. Repetition may reflect non-independent transmission. Put each analytic
rule in one canonical Concept note and link to it instead of scattering weaker
paraphrases.

## Chapter and Section

The Chapter note reconstructs the organizing question and ordered inference. It
links every Section in source order, separates what the scope establishes from
what it leaves open, and identifies the hinge where an inference needs more than
the preceding material supplies.

A Section note follows its pages in source order. It explains the division's
function, links the episodes and concepts introduced there, connects upward to
the Chapter, and states what the division does not establish.

## People

The author note is about the author's role in this exact scope, not a biography.
Distinguish compilation, selection, paraphrase, interpretation, and rhetorical
sequencing; record the author's own caveats and the moves a reader should audit.

Other named people are grouped into role rosters rather than thin pages. Each
roster contains a table with Name, Role in this scope, linked appearance, and
What to be careful about. Do not add biographical knowledge absent from scope.

## Synthesis

Synthesis analyzes rather than retells:

- `argument-map.md` gives the inference chain, support, assumption, and point of
  evidential overreach.
- `claim-evidence-matrix.md` is a literal table with Claim, Owner, In-scope
  evidence, Evidential limit, and linked Notes.
- `motif-matrix.md` is a literal table with one Case Dossier per row and one
  recurring feature per column. A marked cell is a claim about that case's cited
  page. When in doubt, leave it blank.
- `critical-reading.md` gives real strengths alongside applicable limits such as
  selection, heterogeneous source quality, non-independence, transmission,
  translation, missing controls, and compression.
- `open-questions.md` asks what evidence would distinguish readings or settle a
  disputed point. It does not list wiki backlog or material outside scope.

## Navigation

`overview.md` states the organizing question, argument in brief, established/open
pair, neutral-reading rule, and paths to the Chapter, synthesis, and source
guides.

`reading-guide.md` gives:

- a first-read order;
- an audit path from matrix to note to source gateway;
- a lookup path for an episode or concept;
- the PDF page-map path; and
- an explicit warning that the wiki covers only the declared scope.

Each folder catalog lists every note in that folder exactly once as
`- [Title](slug.md) — short hook`. The root catalog lists every semantic note,
all source/reference guides, and `sources/pdf-pages/index.md` exactly once, using
paths relative to the root.

## Repair and deletion

Read before editing. A review repair re-reads both the note and the gateway it
will cite, makes the smallest supported correction, then re-reads both again.
Deleting an unsupportable claim is preferred to leaving it standing. Never
repair a note by changing source infrastructure.

Use `delete_file` only for a model-written duplicate, wrong-path note, or stray
artifact. Never create deletion markers, shell scripts, probe files, aliases, or
temporary notes. No model-facing stage creates or materially rewrites more than
the one or two artifacts explicitly named in its instruction.

## Log

`log.md` is append-only. Add concise entries at the end in this format:

```text
- YYYY-MM-DD [writer] stage: what changed and why
```

The local run audit is the authoritative operational record. The wiki log is a
reader-facing change summary and never claims verification.
